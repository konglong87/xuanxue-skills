# 内容与第三方材料治理

## 允许的工作方式

- 先描述所需能力和可验证规则，再独立设计接口、算法与解释文字。
- 区分传统规则/符号、计算实现、解释性表达。关键词未命中或文本相似度低，不等于法律意义上的原创或不侵权。
- 外部计算器可用于同口径结果比对；记录工具版本与局限，不把源码、课程、图片或叙事案例当作测试数据搬入。
- 外部材料公开可读，不代表自动获得复制、改编或再分发许可。无法确认授权时不引入具体表达或资产。

## 不能采用的做法

- 删除作者、版权、许可证或NOTICE后，把第三方内容当作自有内容发布。
- 搬运课程讲义、视频转录、医案、人物口吻、品牌标识、图像或成套知识文本。
- 把改写、去掉名称、自动改变量名或通过字符串扫描视为合规保证。
- 把源码仓库的MIT声明解释为覆盖第三方商标、专利或未经授权的内容。

## 保留的第三方记录

| 对象 | 使用范围 | 处理方式 |
|---|---|---|
| lunar-javascript | 内联历法运行时 | 保留原LICENSE、版权、上游信息与文件指纹，现有测试校验 |
| iztro固定版本 | 开发期独立数值对照 | 不作为运行时依赖、不分发其源码；保留测试工具版本与生成流程说明 |
| 测试图片的许可说明 | 历史手相测试记录 | 原有作者/许可证记录保留；图片不随仓库分发 |

## 发布防线

1. 调研与审计临时材料放在项目外；如使用 `.research-*` / `.audit-*`，Git忽略并由公开树规则排除。
2. 公开源码树采用批准的根目录/文件清单；新增根目录需人工审查，不自动进入公开树。
3. npm安装包采用 `package.json.files` 清单；实际打包列表另做测试，必须含完整运行时及第三方LICENSE。
4. 发布文件清单只记录载荷，不把旧清单自身纳入新清单，避免不可复核的自引用哈希。
5. 在批准目录内部新增文字、数据或资源，仍需人工审查；路径门禁不进行全文原创性判断。
6. 公共分支、旧标签、GitHub自动源码归档与npm包不是同一发布面；提交前测试同时检查Git跟踪集，拒绝被公开树排除的材料。公开树生成器不能替代历史与内容审查，CI也不能撤回已经推送的内容。

## 对外声明边界

只能报告已检查的版本、文件范围和结果，使用“未发现”而不是“保证无侵权”。版权许可核查不等于专利自由实施分析，也不等于商标审查；商业使用应按目标市场作专业复核。

仓库历史说明还提及其他第三方师承材料。本轮不代表已完成这些历史内容的授权链核查；公开解释性文字、数据编排及其授权应在商业分发前另行复核。
