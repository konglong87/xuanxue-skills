### Phase 2.5 — 八字双向验证与百年用例 ⬜ 未开始（下一步，两个决策已裁决）

出生资料算出八字后，让 agent 用外部来源（AnySearch / WebSearch / 日历 MCP）独立算一遍做对照。

**决策 1 —— 基准来源**：离线多 oracle + 精选真实案例。100+ 条跨百年 / 闰月 / 节气边界 / 换日区间用例由独立实现离线生成进 CI；另人工精选 10~20 条 Rodden AA 级真实出生记录，专门锚定历史时区与夏令时（中国 1986–91 夏令时、民国时区、美国各时区）。**不用网络排盘站当基准** —— 它们口径不一致，会把流派分歧当成错误。

**决策 2 —— 运行时不一致怎么办**：先归因，无法归因才多数投票。用其他选项组合（换日 23:00/00:00 × 真太阳时 开/关）复算，能复现对方结果就说明是流派差异、并列呈现不裁决；任何组合都复现不出才升级取第 2、第 3 个独立来源投票（三次上限），多数一致则以多数为准并显式披露。**不盲从网络** —— 网络排盘源恰好在换日点、真太阳时、立春当日年柱这几个我们刻意暴露的参数上系统性分歧。

## 已确认的决策

记录理由，避免下一个人重新纠结。

1. **新仓库从零建，不迁移任何已有代码。**
2. ~~**技能按术数体系分，不按提问领域分。**~~ **此条已撤回**，理由见开放问题 #1。
   领域技能通过公共接口复用 `bazi`、`core/ganzhi` 与可选 `qimen`，不重复排盘。**已由 [SKILL-TAXONOMY.md](SKILL-TAXONOMY.md) 定稿取代**：混合划分，5 体系 + 2 领域 + 1 共享解法层。
3. **Node.js + jest；全仓库单一 `package.json`，不用 npm workspaces。** 唯一需求是 skills 能调 core、依赖装在一处；Node 的模块解析天然满足。以后真要独立发包，改造是 20 分钟的机械工作。
4. **交付顺序 A′**：`core/` 四层一次建全，再交付第一个技能。理由：命理是唯一能把历法地基压到极限的载荷（四柱 + 节气交界 + 真太阳时 + 大运起运），且有 `BaziGo` 可作对照；先做风水则历法深水区无人验证。
   「`core/` 先行」已锁定；第一个技能定为 `bazi`（八字），见 [SKILL-TAXONOMY.md](SKILL-TAXONOMY.md) 七期优先级。
5. **确定性计算与判断解读分离。** 有唯一正确答案的走 `core/` 并由测试锁定；可以有分歧的交给 LLM。判断标准：两个懂行的人对同一输入是否应该得出完全相同的结果。
6. **流派分歧全部呈现，禁止替用户做决定。** 不选一派，而是全部计算、全部列出、说明各派依据与差异，让用户看到底层原理后自己判断。已知分歧点：
   - **日柱换日点** —— 已定：两套算法都实现，参数 `dayBoundary` 区分，`'23:00'`（子时换日）为默认值，`'00:00'`（子夜换日）需显式传参
   - 玄空飞星是否用替卦
   - 八宅以门定向 / 以坐定向
   - 本命卦男女公式
   - 罗盘坐向 / 纳气盘（见开放问题 #2）
7. **`core/` 每个模块除结构化对象外，另提供 `format()` 输出中文文本**，直接嵌进 prompt。否则四个技能各写一遍 JSON→中文的胶水。
8. **磁偏角用中国城市简表**，不引全球 WMM 模型。（曾一度撤回，现**恢复生效**，见开放问题 #10。）
   资料批判的是「**以磁北为准**」这个做法，不是废弃罗盘这个工具 —— R1 把「八寸罗盘测向」与「卫星地图分析」并列为关键操作。既然实操仍用罗盘读数，就必须把磁北换算成真北，故 `declination()` 保留。同时必须输出误差警示：磁偏角 20 年可变 2°、地磁近日变化早晚不同、钢筋电磁干扰可达 10°+，而风水判定 1° 即天壤之别（明长陵实测偏差 9°）。**卫星地图取真北仍是首选路径，罗盘 + 磁偏角校正是次选。**
9. **`BaziGo` 作校验基准（oracle）**，用于自动生成黄金测试用例，不迁移不修改其代码。
10. **技能路由由 agent 自动完成，写在各 `SKILL.md` 的 `description` 里，不另建调度技能。** 需求方原话「选我们指定这个，还是让 agent 自己决策，我感觉都可以」—— 两者不冲突，取**自动为默认、显式点名可覆盖**：用户不会说"用手相技能"，只会直接发一张手掌照片，自动路由是必需项；而 agent 判断失误时用户要能一句话纠正，所以显式覆盖也是必需项。不另建调度技能的理由是 Claude Code 本就按 `description` 匹配触发，再包一层等于把同一份触发词维护两遍。规范见 Phase 5.5。
11. **判读类输出统一走 `看到的 / 算出的 → 依据 → 结论` 三段式。** 手相尤其吃这一条（判读无确定性计算层可锚定，最容易滑向空泛断语），但四个技能同构。副作用是用户能逐条追问依据出处 —— 这正是"算得准，也说得清"里的后半句。
12. **手相涉健康的表述设红线**：只作体质倾向与精力状态提示，不点名具体疾病、显式声明不构成医疗诊断、建议就医。术数娱乐性质与医疗建议之间必须有明确边界，这一条不接受"用户自己会分辨"的辩解。
